# 第六章 系统测试

## 6.1 测试目的

软件开发完成之后，测试环节的好坏直接决定了系统最终能否交付给用户使用。对乡村振兴管理系统进行完整、规范的测试，一方面是为了核对系统功能是否全部按照需求分析阶段所规划的内容实现，另一方面也是希望在交付之前尽可能多地暴露潜在的逻辑漏洞、权限缺陷和数据一致性问题。由于本系统采用前后端分离架构，后端承担着业务逻辑、数据持久化与权限校验的主要职责，前端则负责页面展示与用户交互，两端之间通过 RESTful 接口进行通信，因此测试工作也相应地划分为两个层面：后端侧重验证接口返回值、状态机流转以及事务一致性，前端侧重验证页面渲染、表单校验与数据回填[14]。只有两端都经过充分的验证，才能保证系统在真实的农户、商家、金融机构与游客手中稳定运行。

## 6.2 测试方式

本系统在测试阶段主要采用黑盒测试的方法，即不关心内部代码的具体实现，而是把每一个功能模块视为一个独立的黑盒，通过构造输入并观察其输出来判断其行为是否符合预期。由于乡村振兴管理系统涵盖了电商交易、旅游预约、金融贷款与保险理赔等多个不同的业务域，其功能之间既相互独立又存在一定的数据依赖，因此在测试设计上采取了"按模块划分、按用例覆盖"的策略，先对每个模块进行独立的功能测试，再通过跨模块的集成场景验证系统整体的流程是否贯通。为了提高回归测试的效率，本文在 src/test/java 目录下借助 Spring Boot Test 与 JUnit 5 编写了一批集成测试用例，采用 H2 内存数据库与 MockMvc 在随机端口上模拟真实的 HTTP 请求，使得每一次代码变更都可以通过一键执行的方式完整回放全部测试流程，进而有效地避免回归缺陷的发生[15]。

## 6.4 系统的测试结论

在完成上述各模块的测试并汇总全部用例的执行记录之后可以看到，乡村振兴管理系统的各项功能均能按照需求分析阶段所制定的预期正常运行：用户认证环节能够正确拦截非法登录并按角色分发权限；农产品电商链路上的库存扣减、订单状态流转、取消回滚等关键事务保持一致性；旅游预约环节的景点审核、评论唯一性约束以及票务预约码生成均符合预期；金融与保险模块在申请、审批、购买、理赔等状态机上流转无误。至此，基于 Spring Boot 与 React 的乡村振兴管理系统整体功能测试工作基本完成，系统达到了可交付使用的稳定状态。

## 6.5 系统开发常规错误

在系统的开发与调试阶段，作者也遇到了不少具有代表性的错误。这些错误看似琐碎，但都曾实实在在地导致了开发进度的停滞。最常见的一类问题是由于本地开发环境中的端口被其他进程占用，导致 Spring Boot 无法在 8080 端口启动，最终通过修改 application.yml 中的 server.port 或释放占用的进程得以解决；其次是在对数据库实体类进行字段调整后未能及时刷新 JPA 的 ddl-auto 配置，导致新加入的字段在 MySQL 中没有同步，前端调用接口时出现字段缺失；此外，还包括 JWT 过期后前端未正确处理 401 响应从而陷入无限重试、文件上传路径在 Windows 与 Linux 下分隔符不一致等跨平台细节问题。通过对这些错误的逐一排查与归纳，作者逐渐养成了在代码提交前自测、在切换环境后回归关键接口的良好习惯。无法访问的典型报错页面如图 6-1 所示。
